# Cherry-pick

## Overview
`git cherry-pick <sha>` **copies** one commit's changes onto the current branch as a **new commit with a new SHA**. The SHA is new because the parent and committer date are different. Git keeps no link between the original and the copy. It's the right tool for a few narrow cases and a source of hard-to-see drift when used as a general way to move work between branches.

## Key Concepts
- **A copy, not a move**: the original stays where it was. You now have two commits with the same diff but different identities.
- **`-x`**: adds `(cherry picked from commit <sha>)` to the message, so you can trace the copy back to the original.
- **Patch-id**: Git can detect copies by their diff (patch-id). `git cherry -v <upstream> <branch>` and `git log --cherry-pick` use it, and `rebase` skips commits whose patch is already upstream. Merge and ancestry checks don't use it.

## Problems When Overused

- **Git doesn't see the copies as the same change.** When the branches meet again, a merge either conflicts (if the code around either copy changed since) or applies cleanly and leaves **the same work in history twice**.
- **Ancestry checks say "not merged".** `git merge-base --is-ancestor <original> develop` returns false even though the code is on `develop`. Branch cleanup scripts, release checks and "is this fix deployed?" queries all get it wrong. Use `git cherry` to check by patch-id instead.
- **Dependencies get left behind.** The picked commit may rely on earlier commits on its branch (a helper, a migration, a config key). The pick then conflicts, or applies cleanly and breaks at runtime.
- **Fixes don't reach the other copies.** A follow-up fix on one copy has to be found and picked again for every other copy. Copies drift apart.

> [!EXAMPLE] Data point
> One repo had the **same commit subject on 13 different commits**, each a cherry-picked copy that drifted from the others. To find yours:
> `git log --all --format=%s | sort | uniq -c | sort -rn | head`

## When to Cherry-pick

| Situation | What to do |
|---|---|
| Moving work `feature` → `develop` → `release` | **Merge the whole branch.** Don't pick commits one by one. |
| Backporting a hotfix to an old release branch | **Cherry-pick with `-x`.** The old release can't take everything else on `develop`. |
| Saving one commit from a branch you'll throw away | **Cherry-pick once**, then delete the branch so only one copy is left. |
| Needing another branch's unmerged work | **Wait for it to merge and rebase**, or **stack your branch on it** and later run `git rebase --onto origin/develop <old-base>`. **Never cherry-pick.** |

> [!TIP] Rule of thumb
> Cherry-pick when the target branch should **never** get the rest of the source branch (old releases, abandoned branches). If the branches will meet again, merge or rebase instead (see [[74.05 Merge vs Rebase Workflows]]).
