# RAG Evaluation

## Overview
**RAG evaluation** scores the **retriever** and the **generator** separately, then end to end. One overall score hides which stage failed: a wrong answer can come from a missed chunk or from a model that ignored a good one. This note covers the metrics, how to build a test set, and how to catch regressions. For general LLM metrics see [[11.15 LLM Evaluation Metrics]]; for the pipeline itself see [[11.12 RAG]].

## Two Stages, Two Sets of Metrics

```mermaid
graph LR
    Q[Query] --> R[Retriever] --> C[Retrieved chunks] --> G[Generator] --> A[Answer]
    GC[Gold chunks] -.-> M1[Recall@K, MRR, nDCG]
    C -.-> M1
    C -.-> M2[Faithfulness]
    A -.-> M2
    Q -.-> M3[Answer relevance]
    A -.-> M3
    GA[Gold answer] -.-> M4[Answer correctness]
    A -.-> M4
```

## Retrieval Metrics
These need **gold chunks**: the chunk IDs that hold the answer for each query. They are cheap, fast and need no LLM.

| Metric | Formula | Answers |
|---|---|---|
| **Hit rate@K** | share of queries with ≥1 relevant chunk in top K | "Did we find anything useful?" |
| **Recall@K** | $\frac{\lvert \text{relevant} \cap \text{top}K \rvert}{\lvert \text{relevant} \rvert}$ | "Did we find *all* the needed chunks?" |
| **Precision@K** | $\frac{\lvert \text{relevant} \cap \text{top}K \rvert}{K}$ | "How much of the context is noise?" |
| **MRR** | $\frac{1}{\lvert Q \rvert}\sum_q \frac{1}{\text{rank of first relevant}}$ | "How high is the first good chunk?" |
| **nDCG@K** | $\frac{\text{DCG@K}}{\text{IDCG@K}}$, $\text{DCG} = \sum_i \frac{2^{rel_i}-1}{\log_2(i+1)}$ | "Is the ranking good, with graded relevance?" |

- **IDCG** is the DCG of the perfect ordering, so nDCG falls in 0 to 1
- Use **Recall@K** for the first stage (the reranker can only fix what was retrieved) and **MRR / nDCG** after [[11.68 Reranking (Cross-Encoders)|reranking]]
- Hit rate equals Recall@K when each query has exactly one gold chunk

> [!WARNING] Gold chunks break when chunking changes
> Gold labels tied to chunk IDs become invalid after re-chunking. Store gold evidence as **document ID + text span** and map it to whatever chunks contain it ([[11.69 Chunking Strategies]]).

## Generation Metrics
These are mostly computed by an **LLM judge**. Names follow RAGAS (Es et al., 2023); TruLens calls the first three its **RAG triad**.

| Metric | Inputs | How RAGAS computes it |
|---|---|---|
| **Faithfulness** (groundedness) | answer, context | Split the answer into claims; score = supported claims / total claims |
| **Answer relevance** | question, answer | LLM writes N questions the answer would fit (default 3); mean cosine similarity to the real question |
| **Context precision** | question, context, reference | LLM marks each chunk relevant or not; average Precision@k over the relevant ranks |
| **Context recall** | context, reference answer | Split the reference into claims; score = claims supported by context / total claims |
| **Answer correctness** | answer, reference answer | Claim-level F1 vs the reference, blended with embedding similarity |

- **Reference-free** metrics (faithfulness, answer relevance) run on live traffic with no labels
- **Reference-based** metrics (context recall, answer correctness) need a gold answer, so they run offline
- Faithfulness ≠ correctness: an answer can copy a wrong chunk faithfully
- Answer relevance does not check facts. A confident wrong answer can score high

> [!INFO] Reading the scores together
> | Pattern | Likely cause |
> |---|---|
> | Low context recall | Retrieval miss: try [[11.65 Hybrid Search (Dense + Sparse)\|hybrid]], [[11.70 Query Transformation\|query rewrite]], better chunks |
> | High recall, low faithfulness | Model ignores or embellishes context: prompt, model, citations |
> | Low context precision, OK recall | Too much noise: rerank, lower K |
> | High faithfulness, low correctness | Corpus itself is wrong or stale |
>
> See [[11.66 RAG Failure Modes]] for the full diagnosis tree.

## LLM-as-Judge Caveats
General judge biases (position, verbosity, self-preference) are in [[11.15 LLM Evaluation Metrics]]. RAG-specific ones:

- **Claim splitting is noisy**: different runs split the same answer into different claims, so scores wobble. Fix the judge model, set temperature 0, and average several runs
- **Judge knows the answer**: it may mark a claim "supported" from its own memory, not the context. Instruct it to use only the given text
- **Long contexts**: judges miss support buried in long chunk lists, the same lost-in-the-middle problem as the generator
- **Score drift**: changing the judge model or prompt changes every score. Pin the judge version, or the baseline is meaningless
- **Validate the judge**: hand-label a sample (50 or so) and check agreement before trusting it. ARES (Saad-Falcon et al., 2023) formalizes this with a small human-labeled set plus **prediction-powered inference** to correct judge error

## Building a Test Set

| Source | Pros | Cons |
|---|---|---|
| **Real user queries** (logs) | True distribution, real phrasing | Need labeling; privacy review |
| **Synthetic** (LLM writes Q&A from chunks) | Fast, cheap, gold chunk known by construction | Too easy: questions echo chunk wording, favor dense retrieval |
| **Expert-written** | Hard, realistic edge cases | Slow, expensive |

Each row should hold: `query`, `gold_doc_ids` / spans, `gold_answer`, and tags (topic, difficulty, query type).

> [!TIP] Test set practice
> - Mix sources: seed with synthetic, then replace with real queries as logs arrive
> - Include **multi-hop**, **no-answer** (answer not in corpus, expect "I don't know"), **keyword/ID**, and **conversational** queries
> - Filter synthetic questions: drop ones that copy the chunk word for word or make no sense alone
> - **Size**: a few dozen queries catches big breaks; a few hundred is needed to trust small differences. With 100 queries and a score near 0.8, one standard error is about 4 points ($\sqrt{0.8 \cdot 0.2 / 100}$), so a 2-point gain is noise
> - Keep a **frozen** regression set and a **growing** set fed by production failures

## Offline vs Online
Generic setup (golden sets, CI gates, canaries) is in [[24.06 Online Evaluation & Prompt Regression]]. RAG-specific signals:

| Offline (before deploy) | Online (live traffic) |
|---|---|
| Recall@K, MRR, nDCG on gold chunks | Reference-free faithfulness / relevance on sampled traffic |
| Context recall, answer correctness vs gold answers | Thumbs up/down, regenerate rate, follow-up "that's wrong" |
| Judge-scored A/B of two configs | **Citation clicks**: users open the cited source (trust signal) |
| | **No-answer rate** and zero-result queries (coverage gaps) |

- Route thumbs-down and no-answer queries into the growing test set

## Regression Testing Retrieval Changes
Changing the **chunker**, **embedder** ([[11.72 Embedding Models]]), K, reranker, or index params ([[23.07 ANN Indexes (HNSW, IVF, PQ)]]) can silently drop recall.

1. Freeze the test set and the judge version
2. Run baseline and candidate on the same queries
3. Compare **retrieval metrics first** (cheap, deterministic), then generation metrics
4. Diff **per query**, not just averages: a flat mean can hide 10 fixed and 10 newly broken queries
5. Slice by tag (IDs, multi-hop, language) to find where it regressed

> [!WARNING] Embedder swaps
> A new embedding model needs the **whole corpus re-embedded**; vectors from two models are not comparable. Evaluate on a full re-index, never a mixed one.

## Tools

| Tool | Type | Strength |
|---|---|---|
| **RAGAS** | Open-source library | The metrics above; synthetic test set generation |
| **TruLens** | Open-source library | RAG triad as feedback functions; app tracing |
