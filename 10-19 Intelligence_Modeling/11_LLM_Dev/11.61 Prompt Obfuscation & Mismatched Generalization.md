# Prompt Obfuscation & Mismatched Generalization

## Overview
**Prompt obfuscation** rewrites a malicious instruction so that character-level detectors miss it while the LLM still understands it. It works because of an **asymmetry**: a regex must match exactly, but an LLM reads distorted text fluently. Anything that is hard for the scanner yet readable for the model gets through — which is why keyword detection for [[11.53 Prompt Injection]] and jailbreaks is a race that cannot be decisively won.

## Obfuscation Forms

| Form | Example |
|---|---|
| **Leetspeak** | `h3ll0`, `1gn0r3` |
| **Homoglyphs** | Cyrillic `а` in place of Latin `a` |
| **Separators** | `i.g.n.o.r.e`, `i g n o r e`, zero-width characters between letters |
| **Full-width characters** | `ｉｇｎｏｒｅ` |
| **Language switch / encoding** | Another language, base64, ROT13 |
| **Splitting across tags** | `ign<b></b>ore` |
| **Thai-specific** | Deliberate misspelling, karaoke romanization, oddly stacked vowels and tone marks |

## Tokenizer-Level View

The tokenizer is not malfunctioning — it just emits an unusual, **out-of-distribution token sequence**:
- `ignore` → one token
- `1gn0r3` → several fragments, e.g. `1` `gn` `0` `r` `3` (illustrative; the exact split depends on the tokenizer)

Early layers effectively reassemble the fragments into a word-level representation, so deeper layers end up with roughly the same meaning as the clean word. The model *understands* — the question is whether its safety behavior comes along.

## Mismatched Generalization

> [!INFO] Wei et al., 2023 — "Jailbroken"
> - **Capability** generalizes to obfuscated text — pretraining data is enormous and contains leetspeak, base64, and every language
> - **Safety training** generalizes less — far less data, mostly clean natural-language text
> - Result: the model can read the request, but its refusal reflex does not fire

- **Base64 requests** — a model fluent in base64 follows an encoded request it would refuse in plain text
- **Best-of-N jailbreaking** — resample random capitalization and character shuffles until one variant slips through
- **More capable models widen the gap** — each new skill (a new encoding, a new language) is new attack surface unless safety training covers it too

### Thai and other lower-resource languages
- Tokenizers split Thai into finer pieces, and Thai safety-training data is likely thinner → cross-lingual prompts have been a known jailbreak route
- Double-edged: obfuscate too heavily and the model can no longer read the payload either

## Countermeasures

| Approach | Strength | Limitation |
|---|---|---|
| **Normalize** (NFKC, Unicode confusables UTS #39, reverse leet) | Collapses many variants into one | Leet is ambiguous (`1` = i or l); corrupts real product codes and numbers |
| **Fuzzy matching** (edit distance) | Tolerates misspelling | Threshold tuning: false positives vs misses |
| **Anomaly signals** (mixed scripts, unnatural digit–letter mixes) | The presence of obfuscation is itself evidence | Must be tuned against legitimate data |
| **ML / LLM classifier** | Understands meaning | The classifier is injectable too; higher cost |

Where the field is heading:
1. **Normalize** before text reaches the model
2. **Train safety on obfuscated data** to close the generalization gap
3. **Detect at the semantic level inside the model** — classifiers or probes on activations rather than on characters

> [!TIP] Key takeaway
> Do not make "catch every spelling" the security boundary. Real protection comes from system design that limits damage when a payload gets through ([[11.54 Agent Tool Sandboxing]]).
