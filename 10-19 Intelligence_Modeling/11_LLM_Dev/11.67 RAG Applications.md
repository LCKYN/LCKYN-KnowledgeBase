# RAG Applications

## Overview
RAG fits any task where answers depend on **private, changing, or citable knowledge** that the model wasn't trained on. Each domain has its own data shape and its own main failure mode, so the right techniques differ by application.

> [!INFO] The core fit
> Use RAG when the knowledge is **too big for the prompt**, **changes often**, or **must be cited**. If none of these apply, a long prompt or fine-tuning may be simpler (see [[#When Not to Use RAG]]).

## Applications by Domain

| Application | Typical data | Main challenge | Key techniques |
|---|---|---|---|
| **Customer support bot** | Help center, past tickets, product docs | Product codes + fuzzy descriptions; outdated articles | [[11.65 Hybrid Search (Dense + Sparse)\|Hybrid]], freshness filters, escalate when unsure |
| **Enterprise knowledge search** | Confluence, Drive, Slack, wikis | Permissions; duplicates; stale versions | ACL filtering at retrieval, dedupe, source citations |
| **Code assistant** | Repos, API docs, issues | Exact symbol names; cross-file dependencies | Symbol + semantic search ([[11.23 Workspace Indexing]]) |
| **Legal research** | Contracts, case law, regulations | Precise wording; citations must be exact | Clause-level chunking, verbatim quotes, citation checks |
| **Medical / clinical QA** | Guidelines, papers, drug labels | High stakes; conflicting or outdated evidence | Source ranking by authority/date, claim verification, human review |
| **Financial analysis** | Earnings reports, filings, transcripts | Tables and numbers; "which company / which quarter" | Table-aware parsing, [[11.44 Contextual RAG]], metadata filters |
| **E-commerce product QA** | Catalog, specs, reviews | Structured attributes mixed with free text | Metadata filters + semantic search; structured data via SQL/tools |
| **Research assistant** | Paper corpora | Multi-hop; summarizing across many papers | Iterative retrieval, [[11.43 Graph RAG]] for themes |
| **HR / policy assistant** | Handbooks, policies by region | Right version for the user's location/role | Metadata filters (region, date), "as of" answers |
| **Agent memory** | Past conversations, user facts | What to store; recalling the right memory | [[11.20 LLM Memory Architecture]], recency + relevance scoring |

## Common Patterns Across Applications

- **Chat over documents**: one corpus, Q&A with citations. The most common starting point
- **Search + summarize**: return top sources *and* a synthesized answer (enterprise search, research)
- **Grounded drafting**: write emails/reports/replies using retrieved facts (support replies, sales proposals)
- **Agentic RAG**: an agent decides when and what to retrieve, possibly across several tools ([[11.11 Agentic LLM]])
- **Structured + unstructured**: SQL/API tools for numbers, vector search for text. Don't embed spreadsheets and hope

> [!EXAMPLE] Support bot, end to end
> User: *"My order #88213 shows delivered but I never got it."*
> - BM25 catches `#88213` → order-status tool call (structured data, not RAG)
> - Dense retrieval finds the "missing package" policy article
> - The answer cites the policy and offers the claim link; if confidence is low, hand off to a human

## Choosing Techniques by Data Shape

| If your data / queries are... | Prioritize |
|---|---|
| Full of IDs, codes, names | Hybrid search (BM25) |
| Long documents with ambiguous chunks | Contextual RAG, parent-child retrieval |
| Questions about the whole corpus | Graph RAG, summarization |
| Short vague questions, generic embedder | HyDE ([[11.64 HyDE vs Standard RAG]]) |
| Access-controlled | Metadata/ACL filtering in the vector store |
| Fast-changing | Incremental indexing, timestamp filters |
| High-stakes (legal, medical, finance) | Reranking, required citations, verification, human review |

## When Not to Use RAG

| Situation | Better option |
|---|---|
| Knowledge is small and stable (fits in a few thousand tokens) | Put it in the system prompt + [[11.21 Prompt Caching]] |
| Need to change **style, format, or behavior**, not facts | Fine-tuning ([[11.31 Supervised Fine-Tuning]], [[11.32 PEFT]]) |
| Answers come from structured data (counts, sums, filters) | Text-to-SQL or API tools ([[11.03 LLM Tool Calls]]) |
| Deep domain language the base model lacks | [[11.33 Continued Pre-training]], then RAG on top |

> [!TIP] Start small
> Begin with plain chat-over-docs on one corpus and an eval set of 50+ real questions. Add techniques only when the eval shows a specific failure ([[11.66 RAG Failure Modes]]).
