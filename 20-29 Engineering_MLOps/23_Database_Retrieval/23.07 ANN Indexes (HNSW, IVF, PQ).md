# ANN Indexes (HNSW, IVF, PQ)

## Overview
**Approximate nearest neighbor (ANN)** search finds vectors that are *probably* the closest to a query, without comparing against every vector. You give up a little accuracy and get large gains in speed and memory. This note goes deeper than the short index list in [[23.01 Vector Databases]]: how each index works, its tuning knobs, filtering, and how to measure it.

## Why Exact Search Does Not Scale
- **Flat (brute-force) search** computes the distance from the query to all $N$ vectors. Cost per query is $O(N \cdot d)$, where $d$ is the dimension
- 10M vectors of 768 float32 dims is about 30 GB of raw data, all scanned on every query
- Fine for small sets or few queries. FAISS notes that for only about 1,000 to 10,000 searches, building an index is not worth it

> [!INFO] The ANN triangle
> Every index trades three things. You can usually pick two.
> - **Recall**: share of the true top-k you actually return
> - **Speed**: queries per second (QPS) or latency
> - **Memory**: bytes per vector in RAM (or disk)
>
> Tuning knobs move you along this triangle. No setting is best for all three.

## Index Families

| Index | How it works | Build time | Memory | Query speed | Updates / deletes |
|---|---|---|---|---|---|
| **Flat** | Scan everything, exact | None | Full vectors ($4d$ bytes) | Slow, $O(N)$ | Easy |
| **IVF** (IVF-Flat) | Cluster, scan nearest clusters | Medium (k-means training) | Full vectors + small overhead | Fast | Adds easy, but clusters go stale as data drifts |
| **HNSW** | Layered proximity graph | Slow | Highest (vectors + graph links) | Very fast at high recall | Adds easy; true deletes hard |
| **PQ / IVF-PQ** | Compress vectors to short codes | Medium (train codebooks) | Very low | Fast, lower recall | Adds easy; needs retrain on drift |
| **ScaNN** | Partition + anisotropic quantization + rescore | Medium | Low | Very fast | Batch-oriented |
| **DiskANN / Vamana** | Graph on SSD, compressed vectors in RAM | Slow | Low RAM, data on SSD | Fast (few SSD reads) | Static in original; FreshDiskANN adds updates |
| **LSH** | Hash so close vectors share buckets | Fast | Low to high (many tables) | Moderate | Easy |

### Flat
- Exact. 100% recall by definition
- The **baseline** every other index is measured against
- FAISS `IndexFlatL2` / `IndexFlatIP` are the only FAISS indexes that guarantee exact results

### IVF (Inverted File)
- Run **k-means** to split the space into `nlist` clusters (also called cells or lists)
- Each vector goes into the list of its nearest centroid
- At query time, find the `nprobe` closest centroids and scan only those lists
- A true neighbor sitting just across a cluster border is missed if its cluster is not probed

### HNSW (Hierarchical Navigable Small World)
- Builds a stack of **proximity graphs**. Top layers are sparse (long jumps), the bottom layer holds every vector (short, precise hops)
- Each vector's top layer is picked at random, with higher layers exponentially less likely
- Search starts at the top, greedily walks toward the query, then drops a layer and repeats
- A neighbor-selection heuristic keeps edges diverse, which helps on clustered data (Malkov & Yashunin, 2016)

### PQ (Product Quantization) and IVF-PQ
- Split each $d$-dim vector into `m` sub-vectors. Run k-means on each sub-space with $2^{\text{bits}}$ centroids (256 for 8 bits)
- Store each vector as `m` centroid IDs. With 8 bits, that is `m` bytes per vector
- Query distance uses **lookup tables**: compute query-to-centroid distances once per sub-space, then sum table entries per code. This is **asymmetric distance (ADC)**: raw query vs compressed database (Jégou et al., 2011)
- **IVF-PQ** combines both: IVF picks the clusters, PQ codes make the scan cheap. Often paired with a **rerank** on full vectors

### ScaNN (Google)
- Three phases: optional **partitioning**, **scoring** with quantized vectors, optional **rescoring** of the top k' with exact distances
- Key idea: **anisotropic vector quantization**. It penalizes quantization error *along* a vector's direction more than error orthogonal to it, because that error changes inner-product scores most (Guo et al., 2020)
- Built for **maximum inner product search (MIPS)**, also supports Euclidean

### DiskANN / Vamana (Microsoft)
- **Vamana** is a graph index tuned so search needs few hops
- The full graph and vectors live on **SSD**. PQ-compressed vectors live in RAM to guide the walk, and full vectors read from SSD rerank the result
- The paper reports billion-point search on one workstation with 64 GB RAM plus an SSD (Subramanya et al., 2019)

### LSH (Locality-Sensitive Hashing)
- Hash functions (e.g. random hyperplanes) put close vectors in the same bucket with high probability
- Strong theory, simple to update. In practice, graph and quantization methods usually reach the same recall with less memory, so LSH is rarely the default today

## Tuning Knobs

| Index | Knob | Raise it to get | Cost |
|---|---|---|---|
| HNSW | `M` (links per node) | Higher recall, better on high-dim data | More memory, slower build |
| HNSW | `efConstruction` (candidate list at build) | Better graph quality, higher recall ceiling | Slower build only |
| HNSW | `efSearch` (candidate list at query) | Higher recall | Slower queries. Must be $\geq k$ |
| IVF | `nlist` (number of clusters) | Smaller lists, faster scans | Need more `nprobe` for same recall, more training data |
| IVF | `nprobe` (clusters scanned) | Higher recall | Slower queries. `nprobe = nlist` is exact search |
| PQ | `m` (sub-quantizers) | Finer codes, higher recall | More bytes per vector. `d` must divide by `m` |
| PQ | `bits` per sub-code | Bigger codebooks, higher recall | Slower training, bigger tables. 8 is the usual default |

> [!TIP] Starting points from primary docs
> - **FAISS HNSW**: `M` between 4 and 64. Memory is about $(4d + 8M)$ bytes per vector
> - **FAISS IVF**: `nlist` between $4\sqrt{N}$ and $16\sqrt{N}$ for under 1M vectors. Train on 30 to 256 vectors per cluster
> - **pgvector IVFFlat**: `lists = rows / 1000` up to 1M rows, `sqrt(rows)` above that. Start `probes` at `sqrt(lists)`
> - **pgvector HNSW**: defaults `m = 16`, `ef_construction = 64`, `hnsw.ef_search = 40`
> - **ScaNN**: `num_leaves` about $\sqrt{N}$; brute force under ~20k points
>
> Fix the build parameters first, then sweep `efSearch` or `nprobe` at query time to hit your recall target.

## Filtering with ANN
Real queries often add a condition: `tenant = X`, `date > Y`. The index was built ignoring that condition, which causes trouble.

| Strategy | How | Problem |
|---|---|---|
| **Post-filter** | ANN top-k first, then drop rows that fail the filter | Selective filters leave too few results. pgvector's example: `ef_search = 40` with a 10% filter returns about 4 rows |
| **Pre-filter** | Apply the filter first, then search only matching vectors | Exact brute force is fine on small subsets. Inside a graph, many nodes are skipped and the walk can get stuck |
| **Filter-aware search** | Check the filter during graph traversal | Needs index support |

- **pgvector** (0.8.0+): **iterative index scans** (`hnsw.iterative_scan`) keep scanning until enough rows pass the filter
- **Qdrant**: filterable HNSW adds extra edges per payload value, but only if payload indexes exist *before* the graph is built. It also uses filter cardinality to pick a strategy
- **Weaviate**: pre-filters with an allow-list from its inverted index. **ACORN** (default since v1.34) uses multi-hop expansion to reach matching nodes faster

> [!WARNING] Low-cardinality filters
> For a filter that matches very few rows, skip ANN: a B-tree index on the filter column plus exact distance is often faster and fully accurate. Partitioning or partial indexes per tenant also work.

## Vector Quantization (Briefly)
Compression of the stored vectors, independent of the index structure. Size ratios below are for float32 input.

| Method | Bytes per dim | Compression | Notes |
|---|---|---|---|
| **float16 / halfvec** | 2 | 2x | Nearly lossless |
| **Scalar int8 (SQ8)** | 1 | 4x | Map each dim's range to 0..255. Small recall loss |
| **Binary** | 1/8 | 32x | Keep only the sign bit, compare with Hamming. Rerank with full vectors |
| **PQ** | `m` bytes total | Tunable, often 16x to 64x | Learned codebooks, highest loss |

- Common pattern: search the **compressed** index for a wide candidate set, then **rescore** with full vectors. pgvector, ScaNN, and DiskANN all document this
- Model-weight quantization is a different topic: [[11.39 Quantization]]

## Measuring an Index
- **Recall@k** = share of the exact top-k (from a Flat baseline) that the ANN index returns. Always compute it against Flat on a sample of real queries
- Plot **recall vs QPS** curves, not one point. Also track build time and index size
- **ann-benchmarks** (ann-benchmarks.com) publishes recall vs QPS curves for many libraries on datasets like SIFT, GloVe, and GIST
- Recall@k of the index is not end-to-end retrieval quality. That is judged with labeled data: [[11.71 RAG Evaluation]]

## Who Uses What

| System | Index types (verified in docs) |
|---|---|
| **FAISS** | `Flat`, `IVF*,Flat`, `IVF*,PQ*`, `PQ`, `HNSW`, `SQ8`, `LSH`, plus OPQ and RaBitQ |
| **pgvector** | `hnsw` and `ivfflat`; `halfvec`, `bit` and binary quantization via expression indexes |
| **Milvus** | FLAT, IVF_FLAT, IVF_SQ8, IVF_PQ, HNSW (+SQ/PQ variants), DISKANN, SCANN, GPU indexes |
| **Qdrant** | HNSW with filter-aware edges |
| **Weaviate** | HNSW with ACORN filtering |

> [!WARNING] Common mistakes
> - Building IVF on an empty or tiny table: centroids are bad. pgvector says to create IVFFlat after loading data
> - Expecting HNSW to free memory on delete. FAISS HNSW does not support removal at all; most HNSW stores soft-delete and clean up later
> - Comparing indexes at default settings instead of at equal recall
> - Using a different metric at index time and query time ([[23.06 Vector Similarity Metrics]])

## Practical Use Cases
- **Under ~100k vectors**: Flat or Flat + SQ8. Simple and exact
- **Fits in RAM, needs high recall and low latency** (most RAG): **HNSW**
- **Memory-bound, tens of millions or more**: **IVF-PQ** with a rerank step
- **Billion-scale on one node**: **DiskANN**
- **Heavy metadata filters**: pick a store with filter-aware HNSW, or partition by tenant
