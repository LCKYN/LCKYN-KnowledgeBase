# API Server Profiling

## Overview
**Profiling** an API server answers three questions before any optimization or rewrite: **what is it waiting on**, **how much CPU and RAM does it use**, and **is that usage stable or spiky**. Always profile **under realistic, steady load** and work **outside-in**: system metrics first, then stack samples, then memory allocations.

> [!WARNING] Measure before rewriting
> A Rust rewrite fixes CPU-bound code and object overhead. It does **not** fix waiting on a slow database, or a model/dataset that is simply large. Profile first to know which problem you have.

## Key Concepts
- **CPU-bound vs I/O-bound**: high CPU + high latency = compute is the bottleneck; low CPU + high latency = the server is **waiting** (DB, Redis, external API, locks).
- **Sampling profiler**: periodically snapshots every thread's stack from outside the process — low overhead, no code changes, safe in production (e.g., **py-spy**).
- **RSS vs PSS vs USS**:
  - **RSS** (Resident Set Size): all pages in RAM, **including shared ones** — summing RSS across forked workers double-counts.
  - **PSS** (Proportional Set Size): shared pages split across the processes sharing them — sums correctly.
  - **USS** (Unique Set Size): memory freed if that process died — the true per-worker cost.
- **Time series beats snapshots**: a single `htop` glance can't tell a leak from a plateau; record CPU/RAM over minutes.
- **Allocation profiler**: records *which call sites* allocated the memory still alive (e.g., **memray**, stdlib `tracemalloc`).

## Tool Map

| Question | Tool | Notes |
|---|---|---|
| Generate realistic load | `oha` | Fixed rate, not max-blast — see [[75.08 oha]] |
| CPU/RAM right now | `htop`, `ps`, `docker stats` | Per-core view reveals single-core saturation |
| Real memory per worker | `smem` | Shows PSS/USS; fixes RSS double-counting |
| Stable or spike (one-off) | `psrecord` | Plots CPU% + RAM of a process tree to PNG |
| Stable or spike (production) | Prometheus + node_exporter + cAdvisor + Grafana | Continuous host/container dashboards |
| Where CPU time goes | `py-spy top` / `py-spy record` | Flame graph, attach to running PID |
| What it waits on | `py-spy record --idle`, OpenTelemetry spans | Idle frames = blocked on I/O or locks |
| What is in memory | `memray`, `tracemalloc` | Live allocations by call site |

## Step 1–2: Load + Snapshot

```bash
oha -z 5m -q 300 http://localhost:8000/heavy-endpoint   # steady 300 req/s for 5 min
ps -eo pid,rss,pcpu,args --sort=-rss | head            # per-worker RSS + CPU
smem -t -k -P uvicorn                                  # PSS/USS: real vs shared memory
```

- **One core at 100%, others idle** → single worker or GIL-bound; more workers or offload CPU work.
- **Sum of USS ≈ total RAM** and every worker is equally large → each worker holds **its own copy** of the same data.

## Step 3: Stable or Spike?

```bash
psrecord <PID> --include-children --interval 1 --duration 300 --plot usage.png
```

| Shape over time | Meaning | Likely cause / fix |
|---|---|---|
| RAM flat and high from startup | Data loaded at boot | Model/dataset per worker → share via `mmap`, model server, fewer async workers |
| RAM **staircase** up under steady load | **Leak** or unbounded cache | memray leak view; cap caches (LRU + size limit) |
| RAM sawtooth | Normal alloc/free or GC cycles | Usually fine — size for the **peak** |
| RAM spikes per request | Large payloads, materializing full results | Stream, paginate, process in chunks |
| CPU pinned on one core | Single-threaded bottleneck | More workers, or move hot path to Rust/C |
| CPU low but latency high | Waiting on I/O | Step 4 — find *what* it waits on |
| Periodic CPU spikes | GC, cron, cache rebuild | Correlate timestamps with scheduled jobs |

> [!INFO] Python RSS rarely shrinks
> CPython's allocator keeps freed memory in its arenas, so RSS can plateau after a spike without being a leak. A leak is **continued growth under steady load**.

## Step 4: What Is It Waiting On?

```bash
py-spy top --pid <PID>                                          # live view of hot functions
py-spy record --pid <PID> --subprocesses --idle -d 60 -o prof.svg  # flame graph incl. waiting
py-spy dump --pid <PID>                                         # every thread's stack, right now
```

- **Wide frames = most time.** With `--idle`, frames in socket reads, `select`/`epoll`, or lock acquisition are **waiting time**.
- Compare with and without `--idle`: if the CPU-only flame graph is thin, the server is **I/O-bound** — Rust won't help much.
- **asyncio caveat**: an idle event loop shows as `select`/`epoll`; py-spy can't tell *which* `await` is slow. Use per-request **tracing spans** ([[24.03 OpenTelemetry]]) to see DB vs HTTP vs compute time per request.
- In Docker, py-spy needs `--cap-add SYS_PTRACE`.

## Step 5: What Is in Memory?

```bash
memray attach <PID>            # attach to a running worker (Linux)
memray run --native -o out.bin -m uvicorn app:app
memray flamegraph out.bin      # live allocations grouped by call site
```

- `--native` shows allocations inside C extensions (NumPy, PyTorch, tokenizers).
- For a quick diff without extra tools: `tracemalloc` snapshots before/after N requests and compare the top lines.

## Findings → Action

| Finding | Action |
|---|---|
| Hot Python function burns CPU | Optimize it ([[71.05 Programmer Performance Micro-Techniques]]), or move just that path to Rust via PyO3 |
| Mostly waiting on DB/Redis/API | Connection pooling, caching, batching downstream calls — language doesn't matter |
| Same data duplicated per worker | Load once and share (`mmap`, separate model server), fewer workers + async |
| Millions of small Python objects | Columnar layout ([[41.04 Apache Arrow]], Polars) — or Rust structs |
| CPU-bound across the whole service | Benchmark a Rust version of the heaviest endpoint first ([[75.06 perf-api-framework]]) |
